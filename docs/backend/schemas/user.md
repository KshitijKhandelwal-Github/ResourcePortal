# User Schemas (`user.py`)

## Overview

The `user.py` file defines data contracts for user accounts, authentication requests, and JWT tokens using **Pydantic**.

In a web application, schemas act as contracts and data filters:
- **Validation**: They ensure incoming data sent by users is structured properly (e.g., that an email looks like `user@example.com` and required fields are present).
- **Security**: They ensure sensitive backend data (like hashed passwords) is never accidentally sent back to the frontend.
- **Serialization**: They convert complex database models into simple JSON objects.

Think of Pydantic schemas like quality control inspectors on an assembly line: they verify that all components meet exact specifications before allowing them into the system, and inspect finished products before shipping them out.

---

## Imports and Dependencies

```python
from pydantic import BaseModel, EmailStr
from typing import Optional
```

Here is why each import is needed:

- **`pydantic.BaseModel`**: The foundation for all Pydantic models. Inheriting from `BaseModel` gives Python classes automatic data parsing, type validation, and JSON serialization.
- **`pydantic.EmailStr`**: A specialized string type that validates whether the given string conforms to standard RFC email format (e.g., rejecting invalid strings like `"not-an-email"`).
- **`typing.Optional`**: Type hint denoting that a field is not strictly required and can be `None`.

## Schema Classes & Fields

### 1. `UserBase`

```python
class UserBase(BaseModel):
    username: str
    email: EmailStr
    role: str = "user"
    cluster_id: Optional[int] = None
```

- **What it does**: Defines shared fields common to all user schemas.
- **Why it's needed**: Avoids code repetition by serving as a base parent class for `UserCreate` and `UserOut`.
- **Fields**:
  - `username` (`str`): Unique handle identifying the user in the system. Required.
  - `email` (`EmailStr`): Validated email address. Rejects malformed email inputs automatically.
  - `role` (`str`, default: `"user"`): Access role of the user (e.g., `"admin"`, `"senior_associate"`, `"user"`).
  - `cluster_id` (`Optional[int]`, default: `None`): Optional foreign key ID associating the user with a specific cluster/department.

---

### 2. `UserCreate`

```python
class UserCreate(UserBase):
    password: str
```

- **What it does**: Validates incoming registration and user creation requests.
- **Why it's needed**: Inherits all fields from `UserBase` and adds the raw `password` string supplied by the user during signup.
- **Fields**:
  - `username`, `email`, `role`, `cluster_id`: Inherited from `UserBase`.
  - `password` (`str`): Plain text password provided by the user. (This will be hashed before being stored in the database).

---

### 3. `UserUpdate`

```python
class UserUpdate(BaseModel):
    email: Optional[EmailStr] = None
    role: Optional[str] = None
    cluster_id: Optional[int] = None
    is_active: Optional[bool] = None
```

- **What it does**: Validates partial updates to an existing user account.
- **Why it's needed**: When an administrator updates a user, they usually only want to change one or two attributes (like toggling `is_active` to deactivate an account) without re-submitting all profile fields.
- **Fields**:
  - `email` (`Optional[EmailStr]`): New email address (optional).
  - `role` (`Optional[str]`): New role assignment (optional).
  - `cluster_id` (`Optional[int]`): New cluster assignment (optional).
  - `is_active` (`Optional[bool]`): Account status flag (e.g., `True` for active, `False` for suspended/disabled).

---

### 4. `UserOut`

```python
class UserOut(UserBase):
    id: int
    is_active: bool

    class Config:
        from_attributes = True
```

- **What it does**: Defines the public-facing response structure returned by API endpoints when returning user profiles.
- **Why it's needed**: It includes database-assigned fields like `id` and `is_active`, but deliberately **omits the password field** so credentials are never exposed over the network.
- **Fields**:
  - `id` (`int`): Unique primary key ID generated by the database.
  - `username`, `email`, `role`, `cluster_id`: Inherited from `UserBase`.
  - `is_active` (`bool`): Whether the account is currently enabled.
- **`Config.from_attributes = True`**: Enables ORM mode. This tells Pydantic to read data directly from SQLAlchemy database model attributes (e.g., `user.email`) instead of requiring dictionary keys (e.g., `user["email"]`).

---

### 5. `LoginRequest`

```python
class LoginRequest(BaseModel):
    username: str
    password: str
```

- **What it does**: Validates the JSON payload sent by the user during login.
- **Fields**:
  - `username` (`str`): User's login handle.
  - `password` (`str`): User's plain text password.

---

### 6. `LoginResponse`

```python
class LoginResponse(BaseModel):
    access_token: str
    token_type: str = "bearer"
    user: UserOut
```

- **What it does**: Structures the response sent back to the client after a successful login.
- **Fields**:
  - `access_token` (`str`): The signed JWT string that the client will store and attach to future requests.
  - `token_type` (`str`, default: `"bearer"`): Standard HTTP authentication scheme indicator.
  - `user` (`UserOut`): Summary profile of the logged-in user.

---

### 7. `Token` and `TokenData`

```python
class Token(BaseModel):
    access_token: str
    token_type: str

class TokenData(BaseModel):
    username: Optional[str] = None
```

- **What they do**:
  - `Token`: Generic schema for representing an authentication token.
  - `TokenData`: Schema holding the payload claims extracted from a decoded JWT (specifically the subject username).
- **Why they're needed**: When verifying a JWT token on protected endpoints, the token decoder extracts the username into a `TokenData` object to confirm who the token belongs to.

---

## Key Concepts

- **Pydantic Validation**: When data is sent to a FastAPI endpoint, Pydantic automatically checks types. If someone sends an invalid email format or leaves out a required field, Pydantic immediately rejects the request with a clear 422 Unprocessable Entity error.
- **Schema Inheritance**: By creating `UserBase`, we avoid duplicating fields across `UserCreate` and `UserOut`, ensuring consistency and maintainability.
- **Data Encapsulation & Safety**: Notice how `password` exists in `UserCreate` and `LoginRequest`, but is completely absent from `UserOut`. This prevents security vulnerabilities where sensitive hash strings could leak to API clients.
- **ORM Mode (`from_attributes = True`)**: Bridges the gap between SQLAlchemy ORM objects (which use object attribute notation `object.field`) and Pydantic models (which expect dictionary-like structures).
